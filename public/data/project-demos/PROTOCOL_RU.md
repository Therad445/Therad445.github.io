## Nginx: выполнен настоящий Java CLI

Сборка: Eclipse Temurin JDK 22.0.2+9, Maven 3.9.6; Linux x86-64. Запущен исходный `io.github.therad445.loganalyzer.Main`. Maven compile прошёл; тесты и статические проверки в этом запуске не выполнялись. Runtime зависимостей сформирован через `dependency:build-classpath`.

Команды, после установки Java 22 и Maven:

```sh
mvn -DskipTests -Dcheckstyle.skip -Dpmd.skip -Dspotbugs.skip -Dmodernizer.skip compile dependency:build-classpath -Dmdep.outputFile=classpath.txt
java -Djava.awt.headless=true -cp "target/classes:$(cat classpath.txt)" io.github.therad445.loganalyzer.Main --source file --path synthetic-access.log --format markdown --export-json report.json --export-csv report.csv
```

Точный генератор входа и запуска: `run-nginx-evidence.py`. Вход содержит 240 записей, три адреса из диапазонов RFC 5737, четыре условных пути и user-agent `SyntheticPortfolioProbe/1.0`. Дата в логах — фиксированное синтетическое время 1 января 2025 года. В нём есть серия из 24 ответов HTTP 500. Telegram-переменные удалены из среды; внешние уведомления не отправлялись.

Приложение выдало:

- 240 запросов; HTTP 200 — 195, HTTP 404 — 21, HTTP 500 — 24;
- средний размер ответа — 960 байт; p95 размера ответа — 1408 байт;
- по 60 запросов к каждому из четырёх ресурсов;
- пустые списки обнаруженных аномалий и подозрительных IP.

`report.json` и `report.csv` — непосредственные экспорты приложения. `report.md` — сохранённый вывод приложения, извлечённый из консольного журнала без переписывания таблицы. После захвата результатов вспомогательное извлечение в harness улучшено: оно обрезает текст по следующей записи логгера, независимо от часа запуска. Сохранённые результаты при этом не пересоздавались. `traffic-original.png` — непосредственный график `ChartGenerator`. `actual-report.svg/png` — отдельно оформленная визуализация значений того же JSON, не интерфейс приложения.

**Оговорка для оригинального графика:** его легенда `reqs/min` не соответствует фактическим единицам. `MetricsAggregator` считает запросы за **20-секундное окно**, а `ChartGenerator` выводит это число без пересчёта на минуту. `errorRate` — доля ошибок, на одной шкале с числом запросов. Иллюстрация сохранена без ретуши. Рекомендуемая подпись: «График, сформированный Java-приложением на синтетических логах. Синяя линия — запросы за 20 секунд (в исходной легенде ошибочно указано reqs/min), оранжевая — доля ошибок».

PDF тоже был получен настоящим `PdfReportGenerator`, но исключён из публикуемого набора. Для его получения пришлось положить этот же сгенерированный график по жёстко заданному пути `src/main/resources/static/traffic_errors.png`; исходный код не менялся. При визуальной проверке PDF обнаружена потеря кириллицы в заголовках. Кроме того, вывод `Анализ занял: 0 мс` не является замером скорости: выражение в исходном `RunBatch` сравнивает две почти соседние текущие отметки, не начало и конец анализа. Ни PDF, ни это число не следует выдавать за качественный результат.

## SRE: реальные процессы и реальный HTTP

Выполнены неизменённые `prober/prober.py` и `sla/sla_calculator.py`, официальный Prometheus 3.16.0 и небольшой локальный HTTP-сервер из `run-sre-evidence.py`. Python 3.12; зависимости проекта: `prometheus_client==0.20.0`, `requests==2.32.3`, `environs==11.0.0`.

Трафик ограничен loopback. HTTP target слушал `127.0.0.1:18770`, prober — `19110`, SLA exporter — `19111`, Prometheus — `19090`. Интервал проб и scrape — 1 секунда; окно SLA — 2 минуты. Последовательность ответов: 10 × HTTP 200, 6 × HTTP 503, 14 × HTTP 200. `SAGE_TOKEN` отсутствовал, внешний push не выполнялся. Все процессы остановлены после снятия результатов.

Запуск после установки зависимостей и распаковки официального Prometheus:

```sh
python -m venv .venv
.venv/bin/pip install -r sre-observability-platform/prober/requirements.txt
.venv/bin/python run-sre-evidence.py
```

Финальный непосредственный ответ `/metrics` экспортёра: `probe_requests_total 30`, `probe_success_total 24`, `probe_failure_total 6`. CSV и график строятся из настоящих последовательных ответов этого endpoint, не из вручную заданной кривой. Счётчики совпадают с журналом локального target.

Prometheus также реально выполнял scrape и запросы: последние сохранённые значения — 23 успеха и 6 ошибок, то есть предыдущая проба относительно финального прямого снимка экспортёра. Последний сохранённый `service_sla_percent` — около 73.1581. Он вычислен самим SLA-кодом через `increase()` по окну, которое длиннее короткого запуска; старт scrape, экстраполяция и разные моменты съёма не позволяют приравнять его к простой доле `24/30`. Это **не показатель доступности production**. На иллюстрации показаны прямые счётчики, а не этот краткий оконный SLA.

В процессе выявлены два ограничения исходников: опечатка в формате logging у prober вызывает сообщения `Logging error`, но не прекращает HTTP-пробы и экспорт метрик; `datetime.utcnow().timestamp()` у SLA зависит от локального часового пояса, поэтому для воспроизводимого запуска задан `TZ=UTC`. Эти ограничения не скрыты исправлением исходного кода.

Контейнеры Docker, Kubernetes, OnCall, MySQL, blue/green и canary в этой проверке **не запускались**. Их манифесты в репозитории не являются доказательством развёрнутого стенда. Рекомендуемая подпись: «Локальный запуск Python prober, Prometheus и SLA exporter. Шесть ошибок HTTP 503 заданы намеренно; график построен по реальному экспорту метрик».

## CUDA: схема исходного кода, без результатов GPU

В окружении отсутствовали `nvidia-smi`, `nvcc` и `/dev/nvidia0`; CUDA-исполнение и сравнение скоростей не выполнялись. Схема `source-flow.svg/png` составлена по `src/knn_cuda.cu` и `src/knn_cpu.cpp` на указанном SHA.

Поток: CPU-матрицы признаков → H2D → CUDA squared-Euclidean pairwise distance kernel → полная матрица расстояний Q × N → D2H → CPU `nth_element` и усреднение целевых значений k соседей. Варианты kernels: naive и tiled через shared memory; блок 16 × 16 потоков, плитка по признакам — 16. GPU вычисляет расстояния; поиск k соседей остаётся на CPU. Матрица float32 требует 4QN байт на GPU и ещё 4QN байт на CPU, помимо признаков и служебной памяти.

`scripts/run_bench.sh` предусматривает N = 5000, 10000, 20000, 50000 при Q = 512, D = 32, k = 5 и seed = 42. Он делает по одному запуску каждой конфигурации, без серии повторов и отдельного прогрева. Для будущего графика скорости нужны реальные GPU/драйвер/CUDA версии, прогрев, повторные измерения, разброс и проверка совпадения предсказаний CPU/GPU. Сейчас никакое ускорение, качество на рынке аренды или производительность на реальном датасете не заявляется.
